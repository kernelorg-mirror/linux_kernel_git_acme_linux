perf-data(1)
============

NAME
----
perf-data - Data file related processing

SYNOPSIS
--------
[verse]
'perf data' [<common options>] <command> [<options>]",

DESCRIPTION
-----------
Data file related processing.

COMMANDS
--------
convert::
	Converts perf data file into another format.
	It's possible to set data-convert debug variable to get debug messages from conversion,
	like:
	  perf --debug data-convert data convert ...

OPTIONS for 'convert'
---------------------
--to-ctf::
	Triggers the CTF conversion, specify the path of CTF data directory.

--to-json::
	Triggers JSON conversion. Specify the JSON filename to output.

--tod::
	Convert time to wall clock time.

--data-type::
	Resolve the data type each memory sample accessed and add it to the
	CTF output, as these fields of the sample events: perf_sample_type
	(the type name, empty when it could not be resolved),
	perf_sample_type_offset (the offset of the access within that type),
	perf_sample_is_write, perf_sample_cpu, perf_sample_addr (the data
	address, which identifies the instance that was accessed) and
	perf_sample_dso_id.  The DSO a type was resolved in is published
	once, as a perf_dso_info event carrying its id, long name and build
	id, which the sample records then reference by id.

	It needs the debug info of the profiled binaries, and samples that
	carry the data address and the CPU they were taken on, as recorded
	by 'perf mem record' or 'perf record -d --sample-cpu'.  Only applies
	to --to-ctf.

	Samples whose data address falls outside the memory range of the
	variable that the recorded IP resolves to are not resolved: the
	recorded IP did not perform the access, which happens when the PEBS
	IP fixup fails, typically for a store sampled while the thread was
	running an interrupt handler -- the recorded IP is the userspace
	instruction that was interrupted while the access went to the
	kernel stack.  These samples are left without the perf_sample_*
	data type fields and their count is reported at the end of the
	conversion; the same counter shows as 'bad_addr' in the data type
	stats, which 'perf report --type-stat' prints for the JSON
	producer and 'perf annotate --type-stat' for the annotation view.

	One record per access is what a consumer needs to tell true from
	false sharing and to suggest which members belong in the same
	cacheline group, which the aggregate histograms exported by
	'perf report -s type --data-type-json' cannot tell: they lose the
	per sample timestamp, CPU and data address.  See the --perf-data-type
	option of pahole for such a consumer.

-i::
	Specify input perf data file path.

-f::
--force::
	Don't complain, do it.

--time::
	Only convert samples within given time window: <start>,<stop>. Times
	have the format seconds.nanoseconds. If start is not given (i.e. time
	string is ',x.y') then analysis starts at the beginning of the file. If
	stop time is not given (i.e. time string is 'x.y,') then analysis goes
	to end of file. Multiple ranges can be separated by spaces, which
	requires the argument to be quoted e.g. --time "1234.567,1234.789 1235,"

	Also support time percent with multiple time ranges. Time string is
	'a%/n,b%/m,...' or 'a%-b%,c%-%d,...'.

	For example:
	Select the second 10% time slice:

	  perf data convert --to-json out.json --time 10%/2

	Select from 0% to 10% time slice:

	  perf data convert --to-json out.json --time 0%-10%

	Select the first and second 10% time slices:

	  perf data convert --to-json out.json --time 10%/1,10%/2

	Select from 0% to 10% and 30% to 40% slices:

	  perf data convert --to-json out.json --time 0%-10%,30%-40%

-v::
--verbose::
        Be more verbose (show counter open errors, etc).

--all::
	Convert all events, including non-sample events (comm, fork, ...), to output.
	Default is off, only convert samples.
